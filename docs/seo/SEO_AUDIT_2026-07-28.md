# Audit SEO complet TOK — 28 juillet 2026

## Résumé exécutif

TOK dispose d'un socle SEO déjà sérieux (canonique `https://www.thetok.ch`, métadonnées sociales, robots.txt, sitemap, schémas JSON-LD et protection HTTP de la majorité des espaces privés), mais son potentiel organique est limité par quatre facteurs structurels :

1. le contenu pré-généré est placé dans `<noscript>` au lieu du HTML initial de l'application ;
2. les listes locales peuvent basculer en 404 côté React lorsqu'aucun restaurant n'est retourné ;
3. le maillage des fiches restaurants dépend trop des clics JavaScript ;
4. l'inventaire public vérifié est encore trop faible pour rivaliser sur les requêtes génériques.

Le code seul ne permet pas de garantir une première position. Google déconseille explicitement les promesses de classement. L'objectif réaliste est d'obtenir d'abord le Top 3 sur des intentions locales étroites et transactionnelles, puis d'élargir la couverture.

Référence : https://developers.google.com/search/docs/fundamentals/do-i-need-seo

## Points solides

- `lang="fr-CH"`, canonicales propres et origine `www.thetok.ch` cohérente ;
- robots.txt accessible et sitemap déclaré ;
- métadonnées title, description, Open Graph et Twitter présentes ;
- schémas Organization, WebSite, Restaurant, Article, Service, FAQ et Breadcrumb déjà amorcés ;
- routes privées principales protégées par `X-Robots-Tag` au niveau Vercel ;
- paramètres de requête retirés des canonicales ;
- routes React chargées à la demande ;
- images des cartes restaurants déjà servies avec `srcset` et `sizes` ;
- build de production configuré pour pré-générer les pages SEO et échouer si la collecte dynamique critique échoue.

## P0 — blocages critiques

### HTML initial trop pauvre

Le générateur injecte le contenu utile dans `<noscript>`, tandis que `#root` reste vide. Le navigateur finit par afficher le contenu, mais le crawl dépend alors davantage de l'exécution JavaScript et des requêtes Supabase.

Action de cette PR : rendre le contenu pré-généré directement dans `#root`, tout en conservant l'application React comme source interactive après montage.

Référence : https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics

### Soft 404 globales

Une URL publique inventée retourne actuellement HTTP 200 avec les métadonnées de l'accueil, avant que React n'affiche éventuellement la page introuvable. La réécriture SPA finale de `vercel.json` en est la cause.

Action suivante : remplacer la réécriture globale par un routage explicite des routes applicatives et une vraie réponse HTTP 404 pour le reste. Cette modification doit être livrée séparément, avec tests de navigation directe sur toutes les routes privées, publiques et dynamiques, car une erreur casserait l'application en production.

### Pages locales incohérentes après hydratation

Une page locale pré-générée peut être indexable dans son HTML, puis devenir une page 404 dans le DOM rendu si la requête catalogue retourne zéro résultat.

Action de cette PR : réserver la 404 aux slugs restaurants réellement inconnus et afficher un état local honnête lorsque l'inventaire est vide. Ne pas étendre l'architecture à de nouvelles combinaisons ville/cuisine/quartier tant que l'inventaire réel ne justifie pas la page.

### Routes utilitaires insuffisamment protégées

Les espaces principaux sont protégés par en-tête HTTP, mais `/espaces` et les redirections de réservation `/r/*` ne faisaient pas partie de la règle commune.

Action de cette PR : ajouter ces préfixes aux protections client et Vercel.

## P1 — gains forts

### Maillage restaurants

Les cartes utilisent principalement des conteneurs et boutons pilotés par `navigate()`, donc les fiches sont moins faciles à découvrir comme liens HTML.

Action de cette PR : transformer le nom et le CTA principal en vrais liens vers le chemin canonique, conserver le suivi analytique et envoyer les créneaux de réservation vers la même URL canonique.

### Données structurées locales

L'`ItemList` statique ne contient pas de `itemListElement`. Les pages locales issues de l'inventaire doivent exposer les restaurants réellement visibles.

Action de cette PR : agréger les restaurants par ville/cuisine pendant le build et produire des ListItem/Restaurant reliés aux fiches canoniques, avec un BreadcrumbList.

Référence : https://developers.google.com/search/docs/appearance/structured-data/local-business

### Sitemap

La date du build est utilisée comme `lastmod` pour presque toutes les URL, y compris lorsque le contenu n'a pas changé.

Action de cette PR : conserver `lastmod` uniquement lorsqu'une date métier réelle existe ; l'omettre sinon. Une étape ultérieure devra paginer l'intégralité de l'inventaire et scinder les sitemaps par type dès que le volume l'exige.

### Actualités dupliquées

Plusieurs actualités peuvent recevoir le même titre de secours `{Restaurant} — actualité restaurant`.

Action de cette PR : construire le titre de secours à partir du contenu réel de la publication et du restaurant, avec une longueur bornée.

### JavaScript et stabilité visuelle

La liste locale chargeait le module lourd du détail restaurant même lorsqu'aucune fiche n'était ouverte. Les images des cartes avaient un ratio CSS mais pas de dimensions intrinsèques.

Action de cette PR : chargement différé du détail restaurant, dimensions 640×400 sur les cartes et navigation canonique.

Actions suivantes :

- séparer plus nettement les shells public et privé ;
- retarder chat, auth et modules de dashboard sur les pages publiques ;
- ajouter dimensions, `srcset` et formats modernes aux autres images ;
- traiter l'image LCP du hero avec `<picture>`, dimensions et priorité explicite ;
- mesurer au 75e percentile : LCP ≤ 2,5 s, INP ≤ 200 ms, CLS ≤ 0,1.

Référence : https://developers.google.com/search/docs/appearance/core-web-vitals

## P2 — optimisations

- raccourcir les titres dépassant environ 60–65 caractères lorsqu'ils perdent leur intention principale ;
- supprimer `meta keywords`, inutile pour Google ;
- vérifier la propriété de `twitter:site="@Tok"` ou retirer la balise ;
- créer des images Open Graph 1200×630 propres aux hubs, restaurants et articles ;
- ajouter `openingHoursSpecification`, `geo`, `menu` et `acceptsReservations` uniquement avec des données fiables ;
- rediriger l'apex HTTP vers HTTPS www en un seul saut ;
- ajouter `hreflang` uniquement lors de la publication de vraies URL traduites et réciproques ;
- ajouter un crawl post-déploiement automatisé : statut, canonical, robots, liens cassés, JSON-LD et Lighthouse mobile.

## Qualité et cohérence des données

L'audit Supabase public montre un inventaire indexable très réduit. La fiche Grand-Chene utilise actuellement une ville/URL `Vernier` alors que l'adresse textuelle mentionne `Chêne-Bourg`. La source correcte doit être confirmée par le restaurant avant toute mutation, puis l'ancienne URL redirigée en 301/308 si le canonical change.

Sans inventaire dense, descriptions, menus, horaires, photos originales et disponibilités réelles, aucune optimisation technique ne permettra de battre durablement TheFork, Michelin, Genève Tourisme, Just Eat ou Uber Eats sur les requêtes génériques.

## Stratégie pour viser le Top 3 local

Priorité 1, uniquement avec données réelles :

- `plat du jour Genève aujourd'hui` ;
- `restaurant disponible ce soir Genève` ;
- `offres restaurants Genève aujourd'hui` ;
- `panier anti-gaspi Genève` ;
- pages ville/quartier/cuisine avec plusieurs adresses vérifiées.

Le meilleur angle défendable est la fraîcheur : menus et disponibilités du jour, prix, photo originale, heure de vérification et transaction immédiate. Ne pas créer de pages quotidiennes ni de combinaisons de filtres sans valeur.

Référence anti-contenu à grande échelle : https://developers.google.com/search/docs/essentials/spam-policies

## Autorité et E-E-A-T

- afficher « informations vérifiées par le restaurant le… » ;
- réserver les avis publics aux réservations/commandes vérifiées ;
- publier une politique d'avis et de modération ;
- signer les guides avec auteur, méthode, date de visite et photos originales ;
- obtenir un lien `Réserver avec TOK` depuis chaque site partenaire ;
- faire ajouter TOK comme lien de réservation/menu/commande dans la fiche Google Business Profile du partenaire ;
- publier des études locales originales : prix du plat du jour, évolution des offres, anti-gaspi et tendances par quartier.

Référence Google Business Profile : https://support.google.com/business/answer/6218037?hl=fr

## Feuille de route

- fusionner et déployer les correctifs de cette PR ;
- corriger les soft 404 par routage HTTP ;

- créer uniquement les pages quartiers/cuisines ayant un seuil d'inventaire ;
- déployer les liens partenaires et Google Business Profile ;
- publier un premier actif éditorial fondé sur des données originales ;
