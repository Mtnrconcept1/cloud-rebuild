Voici le nouvel audit complet de TOK au 7 juin 2026, en tenant compte de l’état actuel du dépôt, du déploiement Vercel, de Supabase et de la production publique.

Verdict général : **TOK a beaucoup progressé techniquement, mais il reste encore plusieurs chantiers avant un lancement commercial sérieux**. Le site public est maintenant bien mieux pré-rendu, le SEO de base est nettement plus propre, les headers de sécurité sont présents en production, et le projet Supabase est actif. En revanche, la page B2B restaurateur est encore trop faible, le manifest PWA est encore ancien, Supabase remonte beaucoup d’avertissements de sécurité/performance, le modèle commercial/commission n’est pas encore intégré dans l’application, et l’infrastructure Vercel reste confuse avec deux projets proches.

Ma note actuelle : **7,3/10**.
Potentiel après corrections prioritaires : **8,5/10**.

## 2. Production et Vercel

Le vrai site public est actuellement servi par le projet Vercel **`cloud-rebuild-recovered`**, qui contient les domaines `www.thetok.ch`, `admin.thetok.ch`, `thetok.ch` et dont le dernier déploiement production est `READY`. 

Le projet Vercel **`cloud-rebuild`** existe aussi, mais son dernier déploiement est en erreur (`readyState: ERROR`) et n’a pas les domaines TOK principaux. 

C’est un risque opérationnel. Tant que deux projets Vercel coexistent avec des noms quasi identiques, tu peux déployer au mauvais endroit, croire qu’un correctif est en ligne alors qu’il ne l’est pas, ou perdre du temps à débugger le mauvais projet.

À faire :

| Action                                                                                              | Priorité |
| --------------------------------------------------------------------------------------------------- | -------: |
| Renommer `cloud-rebuild-recovered` en nom définitif clair, par exemple `tok-production`.            |    Haute |
| Archiver ou désactiver le projet `cloud-rebuild` s’il n’est plus utilisé.                           |    Haute |
| Documenter dans le repo : “Projet Vercel officiel = cloud-rebuild-recovered / domains = thetok.ch”. |    Haute |
| Vérifier que les secrets Vercel production sont sur le bon projet uniquement.                       |    Haute |
| Ajouter une note dans `README_DEPLOY.md` avec procédure de déploiement unique.                      |  Moyenne |

## 9. Supabase : sécurité

Le projet Supabase TOK est actif et sain côté statut global. 

Il y a eu un bon durcissement dans le code : les RPC financières sensibles `generate_restaurant_payout_invoice`, `generate_restaurant_payout_invoice_rpc` et `compute_restaurant_reservation_fees` sont révoquées de `PUBLIC`, `anon` et `authenticated`, puis réservées au `service_role`. 

Le stockage public a aussi été durci : limites de taille/MIME sur les buckets `images` et `invoice-logos`, puis politiques d’upload/update/delete par dossier utilisateur ou restaurant.  

Mais Supabase Advisors remonte encore de nombreux avertissements de sécurité : plusieurs fonctions `SECURITY DEFINER` restent exécutables par le rôle `anon`, comme `auth_can_access_cart`, `auth_can_access_order`, `auth_can_manage_dish`, `donate_points_for_meal`, etc. 

Ce point est **critique**. Certaines fonctions peuvent être volontairement publiques si elles ne retournent qu’un booléen non sensible, mais il faut auditer une par une. Le fait qu’elles soient `SECURITY DEFINER` + exécutables par `anon` doit être justifié explicitement.

À faire :

| Action Supabase sécurité                                                                                    |   Priorité |
| ----------------------------------------------------------------------------------------------------------- | ---------: |
| Exporter la liste complète des warnings `anon_security_definer_function_executable`.                        |   Critique |
| Classer chaque fonction : publique volontaire / à révoquer / à passer en invoker / à déplacer schema privé. |   Critique |
| Révoquer `EXECUTE` de `anon` sur toutes les fonctions non strictement nécessaires.                          |   Critique |
| Ajouter tests SQL/RPC : anon ne peut pas exécuter mutations sensibles.                                      |   Critique |
| Vérifier RLS sur toutes les nouvelles tables business/commerciales.                                         |   Critique |
| Auditer `donate_points_for_meal` en priorité.                                                               | Très élevé |
| Ajouter monitoring des appels RPC publics.                                                                  |      Élevé |

Score sécurité Supabase : **6,5/10**, surtout à cause des advisors encore ouverts.

**TOK ne doit plus seulement montrer qu’il sait faire beaucoup de choses. TOK doit prouver qu’il peut signer, activer et rentabiliser des restaurants sans dépasser ses revenus.**
